# AGENTS.md — правила разработки «БПС Пульт»

Этот файл является постоянной инструкцией для Codex и других разработчиков проекта. Он должен лежать **в корне репозитория** рядом с `index.html`, `app.js` и `styles.css`.

## 1. Назначение проекта

**«БПС Пульт»** — личная mobile-first PWA инженера билетно-пропускной системы стадиона «Мордовия Арена».

Приложение используется для:

- ведения рабочего журнала;
- постановки и контроля задач;
- технических осмотров;
- учёта оборудования;
- подготовки и сопровождения мероприятий;
- настройки фактически используемых гейтов, турникетов, касс, кассиров и систем;
- расчёта готовности мероприятия;
- ведения структурированной базы знаний по БПС;
- локального резервного копирования и восстановления данных.

Приложение должно оставаться быстрым, понятным и пригодным для использования инженером непосредственно во время работы на iPhone.

## 2. Текущее состояние

Текущая стабильная линия проекта:

```text
Версия приложения: 2.5.0
Версия схемы данных: 5
Имя IndexedDB: bps-pult-local
Основной кэш PWA: bps-pult-2.5.0
```

Источники истины для версии:

1. `APP_VERSION` в `app.js`;
2. `VERSION` в `sw.js`;
3. последняя запись в `CHANGELOG.md`;
4. `SCHEMA_VERSION` и `DB_VERSION` в `app.js`.

Все документы, манифест и пользовательский экран версии должны соответствовать этим значениям.

## 3. Архитектурные ограничения

Проект — статическая PWA без сборщика и backend:

- HTML;
- CSS;
- vanilla JavaScript;
- IndexedDB;
- Service Worker;
- GitHub Pages.

Основные ограничения:

- ежедневная работа должна быть возможна без интернета;
- сервер, аккаунты и авторизация не требуются;
- рабочие данные хранятся только локально на устройстве;
- приложение должно открываться из Safari и как установленная Home Screen PWA;
- не подключать runtime-библиотеки через CDN;
- не переводить проект на React, Vite, TypeScript, npm или другой стек без явного решения владельца проекта;
- не добавлять облачную синхронизацию, телеметрию или отправку данных наружу без явного согласования;
- не хранить секреты, токены или пароли в репозитории.

Допускается использовать внешние инструменты только для разработки и тестов, если они не становятся обязательными для запуска опубликованной PWA.

Внутреннее хранилище:

2. явной миграции старых данных;
3. теста перехода со всех поддерживаемых предыдущих схем;
4. сохранения идентификаторов и связей;
5. проверки импорта старых резервных копий;
6. обновления `CHANGELOG.md` и документации.

Нельзя увеличивать версию базы без миграции.

## 6. Критические правила сохранности данных

Потеря пользовательских данных — недопустимая ошибка высшего приоритета.

Обязательные правила:

- считать запись успешной только после `transaction.oncomplete`;
- обрабатывать `transaction.onerror` и `transaction.onabort`;
- обрабатывать `indexedDB.onblocked` и `db.onversionchange`;
- не закрывать форму до подтверждённого сохранения;
- не очищать текущую базу до полной проверки импортируемого архива;
- замену базы выполнять одной атомарной транзакцией;
- при любой ошибке импорт должен полностью откатываться;
- повреждённый архив не должен менять текущие данные;
- обычные удаления направлять в корзину с возможностью отмены;
- связанные ссылки удалять и восстанавливать атомарно;
- диагностический отчёт не должен включать тексты записей, статей, ФИО, адреса, фотографии и другие рабочие данные;
- не ломать импорт `.bpsbackup` и старых JSON-копий.

Перед изменениями в миграциях, backup, import, IndexedDB или Service Worker обязательно создать отдельные тесты на ошибочный сценарий.

## 7. Мероприятия: предметная логика

Мероприятия бывают разными. Нельзя связывать тип мероприятия с жёсткой неизменяемой схемой.

Правильная модель:

```text
Справочник ресурсов объекта
→ шаблон как стартовая конфигурация
→ индивидуальная конфигурация конкретного мероприятия
→ чек-лист только по реально выбранным ресурсам
```

Системы мероприятия настраиваются независимо:

- БПС;
- СИБ: не используется, полностью, частично или резерв;
- онлайн-продажи;
- продажи в кассах;
- печать билетов;
- контроль прохода;
- резервный интернет.

Режимы гейтов должны различать:

- открыт;
- используется частично;
- резерв;
- закрыт по плану;
- не запрошен;
- недоступен.

Режимы турникетов:

- задействован;
- резерв;
- не запрошен;
- закрыт;
- неисправен.

Неиспользуемые и не запрошенные ресурсы не должны снижать готовность.

Закрытый по плану гейт — не неисправность. Недоступный требуемый гейт — проблема.

Кассы и кассиры являются разными сущностями. Поддерживать:

- несколько касс;
- несколько кассиров;
- смены;
- резервные кассы;
- мероприятия без кассовых продаж.

Автоматический чек-лист генерируется только по выбранным системам и ресурсам. При изменении конфигурации выполненные пункты сохраняются по устойчивому ключу, если ресурс и проверка остались актуальными.

## 8. База знаний: предметная логика

База знаний предназначена для поиска информации через год и более. Она не должна превращаться в плоский список заметок.

Поддерживаемые типы материалов:

- инструкция;
- решение неисправности;
- регламент;
- справочная информация;
- чек-лист;
- важная памятка.

Материал должен поддерживать структуру:

- название;
- раздел и вложенный раздел;
- тип;
- статус актуальности;
- краткое описание;
- когда применяется;
- необходимые условия и инструменты;
- последовательные шаги;
- ожидаемый результат;
- действия при неудаче;
- дополнительные сведения;
- теги;
- связи с оборудованием и мероприятиями;
- историю версий;
- дату последней проверки.

Статусы:

- актуально;
- требует проверки;
- черновик;
- устарело;
- архив.

Актуальная статья, не проверявшаяся 365 дней, должна отображаться как требующая проверки.

При содержательном изменении сохранять предыдущую версию. Не допускать бесконтрольного роста истории: текущий лимит — 20 версий, если отдельным решением не введён другой механизм.

Поиск должен учитывать:

- название;
- описание и содержимое;
- шаги;
- теги;
- путь раздела;
- коды ошибок;
- связанные сущности.

## 9. UI и дизайн-система

Интерфейс должен выглядеть как профессиональный рабочий инструмент, а не как AI-generated landing page.

Запрещено без необходимости:

- гигантские hero-карточки;
- декоративные градиенты и свечение;
- дублирование одних и тех же действий;
- случайные размеры отступов;
- множество несогласованных радиусов;
- визуально тяжёлые карточки для каждого небольшого значения;
- наложение подписей на переключатели и поля;
- интерфейс, рассчитанный только на один размер экрана.

Используется 4/8-point grid:

| Назначение | Значение |
|---|---:|
| базовый модуль | 4 px |
| стандартный шаг | 8 px |
| расстояние элементов строки | 12 px |
| внутренний отступ карточки | 16 px |
| боковой отступ страницы | 20 px |
| расстояние крупных секций | 32 px |
| минимальная зона касания | 44×44 px |
| высота основного поля/кнопки | 48 px |
| минимальная высота строки | 72 px |
| радиус поля | 10 px |
| радиус карточки | 14 px |
| радиус bottom sheet | 20 px |

Правила UI:

- контент, шапка, секции и карточки должны стоять на общих вертикальных направляющих;
- одинаковые компоненты имеют одинаковую геометрию во всех разделах;
- формы на iPhone по умолчанию идут в одну колонку;
- две колонки допускаются только при доказанной достаточной ширине;
- текст и controls не должны конкурировать за ширину;
- длинные подписи должны переноситься без наложения;
- нижняя навигация всегда `position: fixed` и находится вне трансформируемой оболочки;
- учитывать `env(safe-area-inset-top)` и `env(safe-area-inset-bottom)`;
- светлая и тёмная темы используют одинаковую геометрию;
- системная строка iOS должна соответствовать активной теме настолько, насколько позволяет WebKit;
- bottom sheet не прокручивает фон;
- поддерживать свайп вниз для закрытия и существующие swipe actions;
- учитывать `prefers-reduced-motion`;
- не использовать конкретные цвета напрямую, если для них уже есть CSS token;
- опасные действия всегда визуально красные.

## 10. Доступность

Каждый новый экран и диалог должен поддерживать:

- семантические элементы `button`, `input`, `label`, `select`, `textarea`;
- понятные доступные названия;
- focus trap в открытом bottom sheet;
- `inert` для фонового интерфейса;
- возврат фокуса на элемент, открывший окно;
- закрытие через Escape;
- отсутствие недоступных кнопок только с иконкой без `aria-label`;
- логичный порядок клавиатурной навигации;
- масштабирование текста без горизонтального overflow;
- разумную работу VoiceOver.

Не удалять outline без равноценного focus-visible состояния.

## 11. Service Worker и обновления

Не активировать новую версию автоматически посреди работы пользователя.

Запрещено вызывать `skipWaiting()` в обработчике `install`.

Правильный процесс:

1. новый worker устанавливается и переходит в waiting;
2. приложение показывает «Доступна новая версия»;
3. пользователь закрывает или сохраняет открытые формы;
4. после подтверждения отправляется `SKIP_WAITING`;
5. приложение перезагружается после `controllerchange`;
6. запускается миграция и проверка целостности.

При каждом релизе обязательно менять версию кэша.

Проверить:

- первый запуск онлайн;
- повторный запуск офлайн;
- обновление со старой версии;
- отсутствие смеси старых и новых JS/CSS;
- fallback навигации на `index.html`.

## 12. Резервные копии

Основной формат стабильной линии — `.bpsbackup`.

Архив должен содержать:

- manifest;
- структурированные данные;
- отдельные вложения;
- контрольные суммы;
- номер схемы;
- версию приложения;
- дату экспорта.

Перед восстановлением:

1. прочитать архив целиком;
2. проверить структуру;
3. проверить контрольные суммы;
4. мигрировать payload в памяти;
5. проверить идентификаторы и дубли;
6. показать preview количества объектов;
7. только после подтверждения выполнять replace или merge.

Для `merge` более свежая запись с тем же id имеет приоритет. Это поведение нельзя менять без отдельной миграционной стратегии и тестов.

Фотографии:

- ограничивать исходный размер;
- обязательно сжимать;
- проверять результат;
- при ошибке сжатия не сохранять бесконтрольно исходник;
- учитывать квоту хранилища.

## 13. Порядок работы Codex

### Перед изменениями

1. Прочитать этот `AGENTS.md` полностью.
2. Изучить структуру репозитория.
3. Прочитать README, CHANGELOG, production checklist, recovery guide и тесты.
4. Найти реальные места реализации задачи, а не угадывать архитектуру.
5. Зафиксировать текущие значения версий и схемы.
6. Выполнить существующие тесты до изменений.
7. Проверить `git status` и не уничтожать чужие незакоммиченные изменения.
8. Составить короткий план работ и критерии готовности.

### Во время разработки

- работать автономно и принимать разумные локальные решения;
- не останавливаться ради мелких уточнений, которые можно безопасно вывести из проекта;
- задавать вопрос владельцу только при действительно архитектурном или потенциально разрушительном выборе;
- не менять несвязанный функционал;
- не переписывать весь проект ради небольшой задачи;
- сначала устранять первопричину, а не добавлять каскад CSS-заплаток;
- переиспользовать существующие компоненты и tokens;
- добавлять регрессионный тест для каждого исправленного бага;
- проверять данные на входе;
- выводить пользователю понятные ошибки без технического мусора;
- не делать ложных заявлений о проверке на реальном iPhone, если проверка выполнена только в эмуляторе.

### После изменений

1. Проверить синтаксис всех изменённых JS-файлов.
2. Запустить все существующие тесты.
3. Добавить тесты новой логики и негативных сценариев.
4. Выполнить UI-аудит на обязательных viewport.
5. Проверить светлую и тёмную темы.
6. Проверить offline shell и update flow.
7. Проверить миграцию предыдущей версии, если менялись данные.
8. Проверить backup, restore, merge и повреждённый архив, если менялось хранение.
9. Обновить документацию и changelog.
10. Сообщить точный список изменённых файлов, тестов, ограничений и ручных проверок.

## 15. Обязательный UI-аудит

Проверять минимум:

```text

375 px
390 px
430 px
```

На каждой ширине проверить:

- главную;
- журнал;
- формы создания и редактирования;
- мероприятия;
- конфигуратор систем;
- гейты и турникеты;
- кассы и кассиров;
- базу знаний;
- редактор статьи;
- оборудование;
- осмотры;
- настройки и восстановление;
- bottom sheets;
- fixed bottom navigation;
- safe-area;
- длинные русские подписи;
- повышенный размер текста, насколько позволяет инструмент.

Критерии:

```text
scrollWidth <= clientWidth

нет обрезанных основных действий
зона касания >= 44×44 px
нижняя панель остаётся fixed после прокрутки
формы не имеют внутреннего горизонтального overflow
```

Сохранять скриншоты только тех экранов, которые действительно проверены.

## 16. Версионирование

Использовать Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

- `PATCH`: исправление ошибки без новой крупной функции;
- `MINOR`: новая совместимая функция;
- `MAJOR`: несовместимая архитектурная или модельная переработка.

Для каждого релиза синхронно обновить:

- `APP_VERSION`;
- `VERSION` и имя кэша в `sw.js`;
- `CHANGELOG.md`;
- README и экран версии;
- manifest при необходимости.

`DB_VERSION` и `SCHEMA_VERSION` повышать только при изменении данных.

## 17. Git и GitHub Pages

Рекомендуемая схема:

```text
main    — стабильная версия, публикуемая GitHub Pages
develop — следующая версия и тестирование
```

Порядок релиза:

1. создать рабочую ветку от актуального `develop`;
2. реализовать задачу и тесты;
3. проверить весь проект;
4. обновить документацию;
5. объединить в `develop`;
6. провести ручную приёмку на iPhone;
7. объединить проверенный код в `main`;
8. создать тег `vX.Y.Z`;
9. дождаться успешного GitHub Pages deployment;
10. проверить опубликованный URL и обновление установленной PWA.

Не выполнять `force push`, переписывание общей истории или удаление веток без явной необходимости.

Не коммитить:

- локальные резервные копии пользователя;
- рабочие данные;
- фотографии из базы;
- диагностические отчёты с чувствительными сведениями;
- временные файлы и тестовые архивы;
- секреты.

Если доступ к GitHub позволяет запись, Codex может подготовить коммит и push. Перед публикацией обязательно показать результаты тестов. Если запись запрещена, подготовить готовые файлы/архив и точную инструкцию загрузки, не утверждая, что публикация выполнена.

## 18. Регламент обновления пользовательского приложения

Перед обновлением пользователь должен:

1. открыть настройки надёжности;
2. проверить целостность базы;
3. создать `.bpsbackup`;
4. сохранить архив в «Файлы» или iCloud Drive;
5. не удалять установленную PWA.

После публикации:

1. дождаться успешного GitHub Pages deployment;
2. открыть PWA без незавершённых форм;
3. нажать «Обновить» в штатном баннере;
4. дождаться перезапуска и миграции;
5. проверить версию и целостность;
6. открыть несколько реальных объектов;
7. создать тестовую запись и перезапустить приложение;
8. создать новую backup уже обновлённой версии.

Откат выполнять выпуском исправленного патча, понимающего актуальную схему данных. Простая подмена старым кодом опасна, если база уже мигрирована.

## 19. Definition of Done

Задача завершена только когда:

- реализована заявленная логика;
- не сломан существующий функционал;
- данные старой версии сохраняются;
- добавлены позитивные и негативные тесты;
- весь набор тестов проходит;
- UI проверен по сетке на обязательных viewport;
- светлая и тёмная темы проверены;
- нет горизонтального overflow;
- нет runtime-ошибок;
- accessibility основных действий сохранена;
- offline и обновление PWA не сломаны;
- версии и документация актуальны;
- сформирован понятный отчёт о проделанной работе;
- все непроверенные на реальном устройстве моменты честно обозначены.

## 20. Формат итогового отчёта Codex

После выполнения задачи сообщить:

```text
Что сделано
Какие файлы изменены
Какая логика добавлена или исправлена
Какие миграции выполнены
Какие тесты запущены и их результат
Какие viewport и темы проверены
Изменилась ли версия приложения/схемы/кэша
Что требуется проверить вручную на iPhone
Опубликовано ли обновление на GitHub Pages фактически
```

Не писать «всё работает», если часть проверок не выполнялась.

## 21. Когда обязательно спросить владельца

Остановиться и запросить решение перед:

- переходом на другой технологический стек;
- добавлением backend или облачной синхронизации;
- изменением модели приватности;
- удалением обратной совместимости backup;
- необратимой миграцией или массовым удалением данных;
- изменением ключевой предметной логики мероприятий;
- публикацией секретных или рабочих данных;
- добавлением платных сервисов;
- крупным редизайном, меняющим привычную навигацию.

Во всех остальных случаях действовать самостоятельно, следуя этому документу и существующему коду.

## 22. Первый запуск Codex в проекте

При первом запуске Codex должен:

1. прочитать `AGENTS.md`;
2. построить карту архитектуры и основных потоков данных;
3. проверить соответствие документации текущему коду;
4. запустить полный набор тестов;
5. найти технический долг и реальные риски;
6. не менять код без необходимости только ради «улучшения стиля»;
7. предложить приоритетный план следующих изменений;
8. после задания пользователя реализовывать задачи небольшими проверяемыми этапами.
