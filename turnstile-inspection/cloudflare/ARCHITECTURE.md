# Многопользовательский осмотр турникетов

Рабочая ветка: `feature/turnstile-team-workflow`.

## Основная модель

- Пользователи: один администратор и сотрудники-инспекторы.
- Жёсткой привязки сотрудника к гейту нет.
- Каждый новый осмотр содержит только реально требуемые гейты: 1, 2, 3 или 4 в любой комбинации.
- Назначение сотрудника выполняется на уровне конкретного гейта конкретного осмотра.
- Гейт можно переназначить после начала работы без потери уже заполненных данных.
- Один сотрудник может получить несколько гейтов.
- Администратор также может быть назначен исполнителем.
- Осмотр завершается автоматически, когда завершены все гейты, включённые именно в этот осмотр.

## UX сотрудника

1. Один раз войти в PWA.
2. При дальнейшем запуске:
   - если назначен один активный гейт — сразу открыть его;
   - если назначено несколько — показать только список его активных заданий;
   - если заданий нет — показать экран «Активных заданий нет».
3. Сохранение каждого изменения автоматическое.
4. Отдельной кнопки «Отправить» нет.
5. Завершение гейта вычисляется автоматически по обязательным полям.
6. При отсутствии сети изменения остаются в локальной очереди и синхронизируются после восстановления соединения.
7. Раздел «История» показывает только работу данного сотрудника.

## UX администратора

- Создание осмотра.
- Выбор произвольного набора гейтов.
- Назначение исполнителя для каждого выбранного гейта.
- Просмотр прогресса в реальном времени.
- Переназначение незавершённого гейта.
- Просмотр истории всех осмотров.
- Просмотр авторства изменений.
- Получение уведомления о завершении выбранного набора гейтов.
- Просмотр/печать/скачивание сформированного акта.

## История и авторство

Текущее состояние каждого турникета хранится в `turnstile_checks`.
Каждое значимое действие дополнительно пишется в `inspection_events`.

Это позволяет показывать:
- кто заполнял конкретный турникет;
- когда он был изменён;
- кто и когда переназначил гейт;
- кто продолжил работу после переназначения;
- историю сотрудника без предоставления доступа к чужим заданиям.

## PDF

PDF строится только из гейтов, включённых в текущий осмотр.

Примеры:
- только 3 гейт → титульник + 3 гейт + итог;
- 1 и 4 гейты → титульник + 1 гейт + 4 гейт + итог;
- все четыре → текущий шестистраничный акт.

После завершения всех выбранных гейтов создаётся запись `documents(status='pending')`.
Клиент с доступным генератором формирует PDF, загружает его в KV и переводит документ в `ready`.
Если документ после формирования изменён, создаётся следующая версия.

## Cloudflare

Планируемая схема:

- Pages / Static Assets — frontend PWA;
- Worker — API и авторизация;
- D1 — пользователи, осмотры, назначения, история;
- Durable Object — realtime-комната конкретного осмотра;
- KV — готовые PDF;
- Web Push — уведомления.

Проект должен работать исключительно в бесплатных лимитах. Платные Cloudflare bindings не добавляются.
